## Общие правила (вставляются в каждый промпт как «железные»)

- **НЕ менять правила боя** (`VladStoneAPI/app/domain/combat/engine/*.py`) —
  кроме A1, где строго добавляется поле `snapshot` и его захват (наблюдаемость,
  не логика). Резолвер/персистенс/роуты не переписывать.
- **Гейты после КАЖДОГО этапа, всё зелёное:**
  - `VladStoneAPI/`: `.\.venv\Scripts\python -m pytest -q` (≥141 passed) +
    `.\.venv\Scripts\python -m ruff check .`.
  - `VladStoneWeb/`: `npm run build` (без ошибок).
- **Коммит на этап** отдельным `feat(battle): … (A_N)`, сообщение на английском,
  не пушить.
- **Браузерную проверку делает владелец/Claude** (у Codex её может не быть).
  Codex обязан: держать build/pytest зелёными; где логика чистая (A1, A2
  `turnPlayback.ts`) — писать юнит-тесты; в отчёте перечислить, что проверить
  руками в браузере.
- CRLF-варнинги git игнорировать. Не трогать `docs/`, кроме отметки статуса.

## Мины (из опыта MVP — НЕ повторить)

- Свой резолв приходит дважды (HTTP-ответ + WS-broadcast) → не проигрывать
  дважды (дедуп по `turn`). Синхронный замок `isPlayingRef`.
- Рендер юнитов в СТАБИЛЬНОМ порядке по `id` (не по массиву) — иначе реордер
  DOM рестартит CSS-анимацию («двойная коллизия»).
- Потолка HP нет (Q4) — плеер должен уметь и РОСТ HP (лечение), не только убыль.
- Watchdog: зависание плеера → форс-финиш на финальный `match` (generation-
  token, чтобы старая корутина не дописывала поверх новой).

## A1 — ✅ Бэкенд: снапшот доски на каждое событие

```
Реализуй подэтап A1 из docs/COMBAT_REWORK.md §22.6 («Контракт снапшота события»).
Сначала прочитай §22 целиком и §22.6.

Цель: каждое CombatEvent, уходящее клиенту, несёт непустой snapshot — состояние
доски НА МОМЕНТ эмиссии события (после мутации этого события).

Файлы: VladStoneAPI/app/domain/combat/engine/apply.py, resolver.py, translate.py;
модель EngineEvent (в apply.py) и CombatEvent (app/domain/combat/models.py, у неё
поле snapshot уже есть).

Шаги:
1. В apply.py: helper board_snapshot(ctx) -> dict, читает ЖИВЫЕ юниты
   (current_hp > 0 и не doomed) + игроков:
   {"units":[{id, card_id, side(value), row, col, current_hp, max_hp, stance(value),
   is_tower}], "players":[{id, mana}]}, где card_id = blueprint_id если он в
   content.CARDS иначе None; stance = current_stance(unit, blueprint);
   max_hp = effective_stats(unit, blueprint).hp; is_tower = TAG_TOWER в тегах.
   Units сортировать по id (детерминизм I3).
2. Добавить поле snapshot: dict в EngineEvent (default пустой dict).
3. Проставлять event.snapshot = board_snapshot(ctx) в момент создания каждого
   EngineEvent ПОСЛЕ мутации состояния — во всех _effect-функциях apply.py и в
   resolver.py (spell_cast/spawned/attack/moved/collision/unit_died/pushed/
   ability_triggered и пр.). Удобно: собрать событие, применить эффект, затем
   проставить снапшот; или единый проход перед возвратом списков, но состояние
   должно соответствовать моменту события (для moved — юнит уже на новой клетке).
4. translate.py: CombatEvent(..., snapshot=fact.snapshot).

Тесты (VladStoneAPI/tests/): у каждого события snapshot непустой; у moved-события
снапшот показывает юнит на НОВОЙ клетке; у unit_died мёртвого в снапшоте нет;
детерминизм (порядок units по id). Существующие 141 остаются зелёными
(добавление поля их не ломает; если payload-тесты сверяют точный dict — обновить).

Проверка: pytest ≥141 + новые, ruff чисто. В отчёте: пример снапшота одного
attack- и одного moved-события.
```

## A2 — ✅ Фронт: движок воспроизведения (данные, без эффектов)

```
Реализуй подэтап A2 из §22.6 («Фронт: модель воспроизведения»). A1 уже сделан
(события несут snapshot). Прочитай §22.6.

Цель: доска проходит по кадрам хода (спавны → итерации → конец), а не прыгает к
финалу. Пока БЕЗ визуальных эффектов — только пошаговая смена состояния доски.

Новые файлы в VladStoneWeb/src/features/battle/:
- animationConfig.ts: константы INTRA_ITERATION_PAUSE≈90, INTER_ITERATION_PAUSE≈600,
  WATCHDOG_MS≈8000 (мс; заглушки под баланс).
- turnPlayback.ts (ЧИСТЫЕ функции + юнит-тесты, без React):
  - applySnapshot(match, snapshot): вернуть новый CombatMatch с юнитами/маной из
    snapshot (юниты по id; HP может и расти — потолка нет; юнита, которого нет в
    snapshot, но он жив в match, оставить — уберёт его death-событие). rows/cols/
    players прочее — из match.
  - groupKey(event): `${event.phase}:${event.micro_step}`.
- useTurnPlayback.ts: хук. playTurn(preMatch, events, finalMatch): async-цикл по
  events — setAnimatedMatch(applySnapshot(cur, e.snapshot)); setActiveEvent(e);
  пауза INTER если groupKey следующего отличается, иначе INTRA; пустые группы
  пропускать; в конце setAnimatedMatch(finalMatch), isAnimating=false. Синхронный
  isPlayingRef-замок; watchdog по WATCHDOG_MS с generation-token → форс-финиш на
  finalMatch.

Интеграция в BattleV4.tsx: в handleResolve вместо setMatch(res.match) сохранить
preMatch=match и запустить playTurn(preMatch, res.events, res.match). Рендерить
доску из animatedMatch во время анимации, из match — в планировании. Блок
планирования при isAnimating (кнопка/клетки disabled).

Тип CombatEvent.snapshot уже в api.ts (проверь; при необходимости уточни поля
units: id, card_id, side, row, col, current_hp, max_hp, stance, is_tower).

Гейты: npm run build зелёный; юнит-тесты turnPlayback (если настроен раннер —
иначе оставить функции чистыми и описать проверку). В отчёте: что проверить в
браузере (юниты появляются/двигаются по шагам).
```
