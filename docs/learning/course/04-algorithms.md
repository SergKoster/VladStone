# Глава 4. Алгоритмы и структуры данных

## Зачем backend-разработчику

Алгоритмы — не коллекция задач на собеседование. Это язык для ответа:
«Что станет дороже при росте матчей, карт, юнитов или соединений?» Структуру
выбирают по операциям и инвариантам, а оптимизируют после измерения.

После главы ты сможешь:

- оценивать время и память через порядок роста;
- выбирать `list`, `tuple`, `dict`, `set`, очередь и heap по операциям;
- замечать скрытые вложенные обходы;
- объяснять сортировку как часть детерминизма;
- отличать алгоритмическую проблему от сетевой/DB latency.

## Входной прогноз

В `MatchChannelManager` соединения хранятся так:

```python
self._connections: dict[str, set[WebSocket]]
```

Почему не `list[tuple[str, WebSocket]]`? Оцени стоимость:

- найти все сокеты матча;
- добавить сокет;
- удалить конкретный сокет;
- broadcast всем `k` сокетам матча.

## 1. Big O — форма роста, не секундомер

`O(1)` означает, что число основных операций не растёт с размером входа
асимптотически; это не «мгновенно». `O(n)` — один пропорциональный обход,
`O(n log n)` — часто сортировка, `O(n²)` — все пары.

Константы, реальные размеры и I/O важны. При 25 юнитах ясный `O(n²)` может
быть лучше сложной индексации. При 200 CCU одна медленная DB query может
доминировать над тысячей Python-операций. Big O отвечает «как масштабируется»,
профилирование — «что тормозит сейчас».

### Быстрый аудит

```python
for unit in units:                # n
    target = unit_at(units, cell) # если внутри линейный поиск n
```

Итого `O(n²)`. Если построить `by_cell = {(u.row, u.col): u for u in units}`
за `O(n)`, последующие lookup близки к `O(1)`. Но индекс надо поддерживать при
движении; цена сложности correctness может быть выше выгоды.

## 2. Структура определяется операциями

| Структура | Сильная сторона | Риск |
|---|---|---|
| `list` | порядок, быстрый append, проход | membership/delete обычно O(n) |
| `tuple` | фиксированная последовательность, hashable при hashable элементах | изменение требует нового объекта |
| `dict` | lookup по ключу в среднем O(1), явная идентичность | память, ключи должны быть hashable |
| `set` | membership/unique/add/remove в среднем O(1) | нет смыслового порядка |
| `deque` | append/pop с обоих концов O(1) | не для произвольного доступа |
| `heapq` | быстро взять минимум/приоритет | не полностью отсортирован, удаление произвольного сложно |

В проекте:

- `set[WebSocket]` — уникальность и быстрое удаление;
- `dict[str, UnitBlueprint]` — lookup blueprint по id;
- `tuple[SpawnIntent, ...]` — намерения после валидации воспринимаются как
  фиксированный input резолва;
- сортированный список units — каноническая сериализация.

## 3. Hashing и идентичность

`dict`/`set` используют hash, затем equality. Ключ должен сохранять hash, пока
лежит в таблице; mutable list поэтому не ключ. Средняя сложность lookup O(1),
не математическая гарантия каждого случая.

Не путай:

- **identity** (`is`) — тот же объект;
- **equality** (`==`) — равное значение;
- **domain identity** — тот же матч/unit по стабильному id.

В ORM две Python-инстанции могут представлять одну DB-строку в разных session.
Доменный id важнее object identity.

## 4. Сортировка, tie-break и детерминизм

Python sort стабилен: равные по ключу элементы сохраняют относительный порядок.
Но если исходный порядок пришёл из `set` или недетерминированного источника,
неполный key не создаёт канон.

`canonical_units_json` сортирует по `unit.id`, а JSON keys — через
`sort_keys=True`. Цель не скорость, а одинаковое представление равного
состояния. Для игрового резолвера tie-break должен быть полным и публичным:
иначе два процесса могут получить разные итоги из того же state.

## 5. Графы и state machine как backend-инструменты

Граф — узлы и связи. В backend это не только маршруты на карте:

- зависимости модулей;
- связи таблиц;
- переходы auth/session;
- фазы матча;
- retry/circuit-breaker states.

State machine помогает запретить переходы:

```text
PLANNING → RESOLVING → PLANNING
                    ↘ FINISHED
PLANNING/RESOLVING → EXPIRED
```

Boolean `is_finished` не выражает, можно ли принимать план и почему матч
закрыт. Enum + таблица переходов делают алгоритм обозримым.

## Разобранный пример: broadcast

Упрощённо:

```python
for websocket in list(connections):
    try:
        await websocket.send_json(payload)
    except RuntimeError:
        disconnected.append(websocket)
for websocket in disconnected:
    disconnect(websocket)
```

Копия `list(connections)` — snapshot iteration: исходный set можно менять
после/вне прохода без ошибки размера. Стоимость `O(k)` по числу подписчиков.
Но latency сейчас **последовательная сумма** отправок: один медленный клиент
может задержать следующих. Big O не показывает backpressure; это глава 14.

### Make

Спроектируй scheduler дедлайнов двумя способами:

1. каждую секунду SELECT всех planning matches;
2. min-heap ближайших дедлайнов.

Опиши операции, сложность, восстановление после рестарта и связь с БД как
источником истины. Реализация не нужна.

## Типичные ошибки

- Оптимизировать по Big O без реального `n` и профиля.
- Использовать set там, где порядок — часть контракта.
- Считать dict lookup гарантированно O(1) во всех условиях.
- Сортировать по неполному ключу и называть результат детерминированным.
- Ускорить lookup индексом, но забыть обновлять индекс при mutation.
- Считать await latency обычной вычислительной сложностью.

2. Когда list лучше set?
3. Какой hidden `O(n²)` встречается чаще всего?
4. Чем identity отличается от equality и domain id?
5. Зачем полный tie-break?
6. Почему broadcast O(k), но может иметь плохую tail latency?
7. Что state machine даёт сверх boolean-флагов?

<details>
<summary>Ответы</summary>

1. Константа может быть большой, операция может включать I/O; O описывает
   рост.
2. Когда важны порядок, дубли, индексный доступ, малый размер или snapshot.
3. Линейный поиск/сортировка внутри линейного обхода.
4. Тот же объект; равное значение; одна бизнес-сущность по стабильному id.
5. Чтобы равный вход давал один порядок независимо от исходного контейнера.
6. Отправки последовательны и одна может долго ждать сеть/backpressure.
7. Явные состояния и допустимые переходы, меньше нелегальных комбинаций.
