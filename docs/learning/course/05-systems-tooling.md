# Глава 5. ОС, CLI, Git и системная отладка

## Результат

Backend работает не «в Python», а в процессе ОС: с файловой системой,
переменными окружения, портами, сигналами, памятью и другими процессами.
Профессиональная отладка — управляемое уменьшение пространства причин, а Git —
журнал проверяемых решений.

После главы ты сможешь:

- различать программу, процесс, поток и coroutine;
- объяснять адрес/порт, cwd, environment и lifecycle процесса;
- уверенно исследовать репозиторий через `rg`, логи и точечные команды;
- локализовать дефект гипотезами, а не случайными правками;
- создавать маленькие осмысленные Git-коммиты без потери чужой работы.

## Входной сценарий

API отвечает на `127.0.0.1:8001`, но не на `localhost:8001`; тесты иногда
цепляют dev-БД; порт занят после падения терминала.

Разложи возможные причины по уровням: имя хоста, сокет/порт, процесс, cwd,
environment, импорт Python, cookie. Какие две команды дадут максимум
информации без изменения состояния?

## 1. От файла до процесса

Файл `python.exe` — исполняемая программа. Запуск создаёт **процесс** со своим
виртуальным адресным пространством, таблицей открытых файлов/сокетов,
environment, cwd и как минимум одним потоком.

**Поток** — последовательность исполнения внутри процесса; потоки разделяют
память и потому требуют синхронизации. **Coroutine/task** — объект
кооперативной конкурентности, который исполняется потоком event loop и отдаёт
управление на `await`.

```text
Windows
└─ python.exe process (uvicorn)
   ├─ main thread
   │  └─ asyncio event loop
   │     ├─ HTTP task
   │     ├─ WebSocket task
   │     └─ timer worker task
   ├─ thread-pool threads (sync work framework)
   ├─ file/socket handles
   └─ virtual memory
```

Один процесс может держать сотни I/O-задач, если они быстро доходят до
неблокирующего `await`. CPU-цикл или синхронное I/O внутри event-loop thread
останавливает прогресс всех его задач.

## 2. Адрес, порт и сокет

IP отвечает «на каком сетевом интерфейсе», порт — «какому слушающему сокету
процесса». `127.0.0.1` — loopback IP. `localhost` — имя, которое резолвится
обычно в loopback, но браузер видит другое hostname для cookie/origin.

Слушать `127.0.0.1` означает принимать локальные подключения на этом адресе.
Слушать `0.0.0.0` — на всех IPv4-интерфейсах; это не адрес для клиента, а
bind-намерение сервера.

Полезные read-only проверки PowerShell:

```powershell
Get-NetTCPConnection -LocalPort 8001 -ErrorAction SilentlyContinue
Get-Process -Id <pid>
Resolve-DnsName localhost
```

Не убивай процесс до идентификации владельца и причины.

## 3. cwd и environment

Относительный путь считается от current working directory процесса, не от
файла с кодом. Поэтому `sqlite:///./vladstone_dev.sqlite3` зависит от того,
откуда запустили API.

Environment наследуется процессом при старте. `Settings()` читает его, а
`@lru_cache` сохраняет результат. В `app/db/session.py` engine создаётся на
уровне импорта:

```python
settings = get_settings()
engine = create_engine(settings.database_url, ...)
```

Следствие: поменять `DATABASE_URL` после импорта недостаточно. `tests/conftest.py`
устанавливает env **до** импорта приложения — это часть изоляции, не
магическая настройка pytest.

Прогнозируй:

```powershell
$env:DATABASE_URL='sqlite:///./scratch.sqlite3'
.\.venv\Scripts\python -c "from app.db.session import engine; print(engine.url)"
```

Новая команда создаёт новый процесс и читает новое environment. Изменение env
в одном терминале не переписывает уже работающий uvicorn.

## 4. CLI как лабораторный прибор

Каждая команда должна отвечать на вопрос.

```powershell
rg -n "resolve_v4_turn" VladStoneAPI
rg --files VladStoneAPI\app
git status --short
git diff -- docs\learning
.\VladStoneAPI\.venv\Scripts\python -m pytest `
  VladStoneAPI\tests\test_combat_resolve_race.py -q
```

Сначала сузь область, затем читай. Рекурсивный дамп всего репозитория создаёт
не информацию, а шум. Для Python запускай инструмент через интерпретатор
нужного venv: `python -m pytest` связывает команду и environment.

## 5. Отладка как цикл гипотез

```text
Наблюдение → минимальное воспроизведение → граница «работает/сломано»
→ гипотеза → различающий эксперимент → новый факт → причина → регресс-тест
```

Хорошая гипотеза фальсифицируема:

> «Если тесты используют dev-БД из-за поздней установки env, то URL engine,
> напечатанный после импорта, останется dev; если env выставить до импорта —
> станет temporary».

Плохая:

> «Наверное, SQLAlchemy заглючила».

Меняй одну переменную. Логируй идентификатор запроса/матча, фазу и факт, а не
«зашли сюда». После причины сначала создай падающий тест, затем исправляй.

### Двоичный поиск по слоям

Если UI не получил событие:

1. state в БД обновлён?
2. сервис вернул events?
3. HTTP/WS payload содержит events?
4. браузер получил frame?
5. playback принял ключ?
6. React state изменился?
7. CSS отрисовал?

Каждый ответ делит пространство. Не правь анимацию, пока payload не проверен.

## 6. Git как страховка мышления

Перед работой:

```powershell
git status --short
git branch --show-current
git log -5 --oneline
```

Различай:

- working tree — файлы на диске;
- index/staging — снимок будущего коммита;
- commit — неизменяемый объект истории;
- branch — двигающаяся ссылка на commit.

Профессиональный commit:

- решает одну связную задачу;
- включает код, тест и нужную документацию;
- не захватывает чужие изменения;
- имеет сообщение о результате: `fix(battle): keep timer worker alive`;
- проходит релевантные проверки.

`git diff` показывает unstaged, `git diff --staged` — будущий commit. Не
используй destructive reset/checkout для «чистоты», если не доказал, что
изменения твои.

## Разобранный пример: тестовая БД

`tests/conftest.py`:

1. строит уникальный temporary path с PID;
2. удаляет старый файл этого прогона;
3. устанавливает `DATABASE_URL`;
4. только затем тестовые модули импортируют app;
5. `app.db.session` создаёт engine на правильном URL.

Инвариант: тест не пишет в накопительную dev-БД. Failure mode — ранний импорт
app сторонним plugin/module до `conftest`.

## PRIMM

### Predict

Что напечатают два процесса?

```powershell
$env:ENVIRONMENT='test'
python -c "import os; print(os.getenv('ENVIRONMENT'))"
Remove-Item Env:\ENVIRONMENT
python -c "import os; print(os.getenv('ENVIRONMENT'))"
```

### Run

Выполни безопасные команды `git status`, `git branch --show-current`,
`Get-NetTCPConnection` для 8001/5173. Сначала запиши ожидаемый результат.

### Investigate

Проследи момент чтения config: `core/config.py` → `db/session.py` →
`tests/conftest.py`. Нарисуй import timeline.

### Modify

В отдельном мини-проекте создай модуль, который читает env при импорте, и
функцию, читающую при вызове. Измени env между импортом и вызовом. Объясни
разницу.

### Make

Возьми реальный закрытый баг из `TODO.md`. Не исправляя его, составь debug
plan: наблюдение, три уровня, две конкурирующие гипотезы, различающий
эксперимент, ожидаемые логи и будущий regression test.

## Самопроверка

1. Чем процесс, поток и task отличаются по памяти и планированию?
2. Почему `localhost` и `127.0.0.1` могут вести к разным auth-результатам?
3. Когда читается env в текущем DB setup?
4. Зачем гипотезе различающий эксперимент?
5. Почему сначала ищут границу отказа?
6. Что именно показывает staging area?
7. Какие четыре свойства у хорошего commit?

<details>
<summary>Ответы</summary>

1. Процессы изолируют адресное пространство; потоки разделяют его и
   планируются ОС; tasks кооперативно исполняются event loop.
2. Это разные hostname/origin и cookie scope, даже если IP совпал.
3. При импорте `app.db.session`, через cached settings и создание engine.
4. Он должен дать разные результаты, если гипотеза верна или ложна.
5. Это резко сужает слой и исключает случайные правки downstream.
6. Точный снимок файлов/строк, который станет следующим commit.
7. Один смысл, полный комплект сопутствующих изменений, отсутствие чужого,
   зелёные проверки и осмысленное сообщение.
