# Глава 3. Типы и моделирование контрактов

## Главная идея

Типы ценны не украшением сигнатур, а количеством ошибочных состояний, которые
невозможно или трудно представить. Хорошая модель переносит проверку с
«помним в каждом `if`» в одно место создания значения.

После главы ты сможешь:

- читать union, generic, `Annotated`, `Protocol` и type narrowing;
- различать статическую проверку и runtime-валидацию;
- моделировать состояния enum/discriminated union вместо «словаря всего»;
- находить shotgun parsing и невыразимые инварианты;
- выбирать контракт для публичной границы и внутреннего домена.

## Входной прогноз

Что опасного в модели:

```python
class Card(BaseModel):
    card_type: str
    blueprint_id: str | None = None
    spell_id: str | None = None
```

Перечисли все логически недопустимые комбинации полей. Сможет ли аннотация
`str | None` сама остановить их при runtime?

## 1. Три уровня контракта

```text
Документированный смысл
        ↓
Статический тип (IDE/type checker)
        ↓
Runtime-проверка (Pydantic/явный код/constraint БД)
```

Они дополняют, но не заменяют друг друга. Аннотация помогает до запуска, если
код проверяет type checker. Pydantic защищает процесс от конкретных данных.
Constraint БД защищает общую истину даже от другого процесса.

В текущем `pyproject.toml` нет mypy/pyright: аннотации улучшают читаемость и
IDE, но отдельный строгий type-check gate пока отсутствует. Не говори
«типобезопасно», если инструмент не запускался и граница не валидируется.

## 2. Union и narrowing

`A | B` означает «одно из», а не «немного обоих». Полезная модель карты:

```python
class UnitCard(BaseModel):
    kind: Literal["unit"]
    blueprint_id: str

class SpellCard(BaseModel):
    kind: Literal["spell"]
    spell_id: str

Card = UnitCard | SpellCard
```

После проверки `card.kind == "unit"` type checker может сузить union и
разрешить `blueprint_id`. Невозможны «spell без spell_id» и «unit с обоими
id». В реальном проекте `CardDefinition` использует одну модель и
`model_validator`, что тоже валидно: сравни выразительность, совместимость
payload и цену рефакторинга, прежде чем предлагать union.

`Optional[T]`/`T | None` означает реальную семантическую возможность
отсутствия. Не используй `None` для трёх разных смыслов вроде «не загружено»,
«не найдено», «не применимо» — это три состояния, им нужна явная модель.

## 3. Generic: связь между типами

Generic полезен, когда контракт связывает вход и выход:

```python
T = TypeVar("T")

def first(items: Sequence[T]) -> T | None:
    return items[0] if items else None
```

Без `T` ответ был бы `object | None`, и знание о типе элемента терялось бы.
Не вводи generic только для «красивой сложности»: если связи нет, обычный тип
яснее.

## 4. Protocol: тип по поведению

В `app/services/combat_matches.py`:

```python
class CombatMatchStore(Protocol):
    def get(self, match_id: str) -> CombatMatchRecord | None: ...
    def save(self, record: CombatMatchRecord, match: MatchState) -> None: ...
```

Protocol описывает нужное поведение без наследования. Любой объект с
совместимыми методами подходит структурно. Это делает dependency direction
явным: сервис зависит от способности хранить матч, не обязательно от
SQLAlchemy.

Ограничение проекта: сам Protocol пока не является везде внедрённой границей —
часть функций всё ещё создаёт `SqlAlchemyCombatMatchStore` напрямую. Тип
интерфейса не гарантирует архитектурного decoupling, пока composition root не
передаёт реализацию.

## 5. `Annotated`: тип плюс метаданные

```python
DbSession = Annotated[Session, Depends(get_db)]
```

Для type checker это `Session`; FastAPI читает метаданные `Depends(get_db)`.
Так один параметр несёт статический тип и runtime-инструкцию DI. Не путай с
конструированием `Session`: объект создаёт dependency.

## 6. Инвариант и источник истины

В `engine/validation.py` проверяется:

- уникальность unit id и клетки;
- ссылки на известные blueprint/status/tag;
- допустимые координаты;
- положительное HP после death wave;
- неотрицательный action budget;
- mana и hand cap.

Это хорошая checkpoint-модель: локальные Pydantic-инварианты проверяются при
создании объекта, межобъектные — на границе фазы. Важен момент проверки.
`current_hp <= 0` временно допустим внутри death wave, но не после неё.
Слишком ранняя проверка отвергнет легальный промежуточный state; слишком
поздняя потеряет источник дефекта.

## Разобранный пример: intent как недоверенные данные

Путь:

```text
JSON request
  → ResolveTurnRequest
  → PlacementRequest / SpellRequest
  → _build_intents
  → PlayerIntents / SpawnIntent / SpellIntent
  → domain validation + resolver
```

Каждый переход сужает множество значений. Pydantic request проверяет форму и
`turn >= 1`; intent-модель проверяет согласованность клетки; домен проверяет
руку, ману, spawn zone и текущий state. Нельзя считать корректный JSON
корректным игровым действием: schema-valid ≠ domain-valid.

### Run

### Investigate

- какие ошибки он способен обнаружить;
- какой контекст у него есть;
- каким типом/исключением сообщает ошибку.

### Modify

Сделай вне проекта маленькую модель результата:

```python
class Success: ...
class NotFound: ...

```

Напиши `render(result)` с `match/case`. Затем добавь новый вариант и посмотри,
предупредит ли текущий инструмент о неполном `match`. Это покажет разницу
между идеей exhaustive check и фактической конфигурацией проекта.

### Make

Спроектируй тип `CardInstance` для будущего runtime deck: `instance_id`,
`card_id`, modifiers. Письменно зафиксируй:

- что валидирует сама модель;
- что требует каталога;
- что требует состояния игрока;
- что никогда не должно сериализоваться сопернику.

Не внедряй: это архитектурная будущая задача из документов, а не учебная
лицензия на изменение модели.

## Частые ошибки

- `dict[str, Any]` на постоянной внутренней границе уничтожает помощь типов.
- Один boolean на состояние с тремя фазами приводит к нелегальным
  комбинациям нескольких флагов.
- Validator с I/O делает создание модели непредсказуемым и плохо тестируемым.
- Type cast не проверяет runtime и может просто заставить type checker
  замолчать.
- `Protocol` без внедрения зависимости — декларация намерения, не
  автоматическая архитектура.

1. Какие ошибки ловят type checker, Pydantic и constraint БД?
2. Чем union лучше набора nullable-полей?
3. Когда `None` скрывает несколько состояний?
4. Какую связь выражает generic?
5. Чем Protocol отличается от базового класса?
6. Почему межобъектный инвариант проверяют на checkpoint?
7. Почему schema-valid request может быть нелегальным ходом?

<details>
<summary>Ответы</summary>

1. Статическую несовместимость до запуска; форму конкретных runtime-данных;
   общую durable-истину соответственно.
2. Делает допустимые варианты явными и сужаемыми, исключает смешанные формы.
3. Когда «нет» имеет разные причины/переходы и от них зависит поведение.
4. Зависимость выходного типа или нескольких параметров от одного входного T.
5. Protocol структурный: важна форма поведения, наследование не обязательно.
6. Там доступны все связанные объекты и состояние уже обязано быть
   согласованным.
7. Schema знает форму, но не руку, ману, владельца, фазу и правила поля.

</details>
