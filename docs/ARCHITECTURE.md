# VladStone — Архитектура

> Фиксирует фактическое устройство кода и целевые изменения под релизный план
> ([DESIGN.md](DESIGN.md) §11). Правило: при изменении структуры кода/API/моделей —
> обновлять этот файл. Числа и константы не дублируются — ссылки на файлы-источники.

## 1. Обзор системы

```
[Браузер: React/Vite/TS SPA]
   │  HTTPS JSON (fetch, cookie refresh_token)
   │  WebSocket /ws/matches/{id}
   ▼
[FastAPI (uvicorn), VladStoneAPI]
   ├─ api/routes: health, auth, me, combat, telemetry, ws
   ├─ services: матчи, награды, аккаунты, таймеры, payloads
   ├─ domain/combat: чистые правила боя (без I/O)
   ├─ realtime: in-process менеджер WS-каналов матчей
   ▼
[SQLAlchemy → SQLite (dev) / PostgreSQL (prod, docker-compose)]
[Redis — в compose, зарезервирован под multi-instance pub/sub (не используется)]
```

Принцип: **сервер авторитетен во всём** (бой, коллекция, награды); клиент шлёт
намерения и отрисовывает серверные события.

## 2. Backend

### 2.1 Домен боя — `app/domain/combat/`

Чистый слой: pydantic-модели, никакого I/O. **Live-бой с июля 2026 работает
через `app/domain/combat/engine/` и `BattleStateV4` (`RULESET_VERSION` 3).**
Модули MVP в корне `domain/combat/` ниже остаются legacy-кодом и частью старых
тестов, но API/таймер/WS их больше не резолвят. Их нельзя считать источником
текущих правил или каталога; удалить после переноса коллекции (§8.18).

Legacy-модули MVP:

| Модуль | Ответственность |
|---|---|
| `models.py` | MatchState, UnitState, PlayerState, CardDefinition, CombatEvent, enums |
| `constants.py` | Размер поля, HP башни, мана-кап, тайминги ходов и буфер анимации |
| `board.py` | Правила поля/маны: расписание прироста, клетки спавна, направление стороны, награда за результат |
| `cards.py` | Каталог карт (единственный источник статов), DECK_CARD_IDS |
| `factory.py` | Создание матча/юнитов, инициализация колоды |
| `deck.py` | Цикл колоды: раздача руки, добор, перетасовка, проверка руки |
| `planning.py` | apply_placements: валидация спавна, мана, рука (from_hand), выталкивание |
| `resolver.py` | resolve_turn: цикл микроходов, добор, восстановление очков действий, таймер |
| `attacks.py` | Намерения атак; фазовое применение урона без оверкилла |
| `movement.py` | Намерения движения, применение с конфликтами клеток |
| `collisions.py` | Одновременный вход в клетку: размен ударами |
| `targeting.py` | Выбор целей (ближний юнит в колонке, башня в радиусе) |
| `events.py` | Эмиссия событий + снапшот состояния на момент события |
| `timing.py` | Дедлайн планирования; буфер на клиентскую анимацию резолва |
| `lifecycle.py` | Смерти (DEATH-события), завершение матча, награда |
| `bot.py` | Тестовый бот: чередование толстяк→лайн 0 / дальник→лайн 1, копит ману |
| `helpers.py` | Мелкие выборки: юнит в клетке, игрок по id |
| `rules.py` | Фасад домена: реэкспорт публичного API (роуты импортируют отсюда, а не из внутренних модулей) |

**Конвейер микрохода** (`resolver.resolve_micro_turn`):
1. Для каждого живого юнита собирается намерение (атака/движение по приоритету) —
   ни одно не применяется во время сбора.
2. Фаза атак: `apply_attack_intents` — урон копится по целям, события эмитятся с
   инкрементальным before/after HP; юнит не тратит атаку на уже обречённую цель.
3. Фаза движений: `apply_move_intents` + `collisions` (одновременный вход двух
   юнитов в клетку = размен ударами).
4. `remove_dead_units` (DEATH-события) → `finish_match_if_needed`.
Цикл повторяется, пока есть действия; затем ход++, мана, добор карты,
восстановление очков действий (планирование показывает полный бюджет), новый
дедлайн = буфер анимации (по числу событий) + время хода
(`timing.turn_duration_seconds`: эндшпиль сжимает его с ростом номера хода,
DESIGN §3.5; match payload несёт готовое `planning_seconds` — клиент капает им
видимый таймер и формулу не дублирует). (При вводе
оверлея «итерация N» — прибавить к буферу фиксированное время баннеров на
итерацию, COMBAT_REWORK §18.3.)

**Контракт combat events** (основа клиентских анимаций):
`type, actor_id, target_id, target_kind, damage, from/to_position,
before_hp/after_hp, sequence, micro_step, ability_trigger, effect_kind, wait_reason, affected_cells,
snapshot{players,units}`. `affected_cells` — полная визуальная область события
на поле, включая пустые клетки; её вычисляет сервер из того же selector, что и
реальные цели, а клиент только отображает.
Для `ability_triggered` `ability_trigger` и `effect_kind` переносят хук и
примитив эффекта структурно (например `on_death` + `deal_damage`); UI не
выводит их из `message`, поэтому визуально различает смерть и спавн.
Для `unit_waited` `wait_reason` — server-authoritative enum
`defense_no_target|attack_no_target|path_blocked|no_action_budget`; он только
объясняет отсутствие действия и не меняет поле, бюджет или правила. Клиент
показывает локализованный бейдж по enum, а не выводит причину по стойке/каталогу.
Структуры (тег `structure`, т.е. башни) wait-события не эмитят: они не ходят по
определению, а их «ожидание» лишь раздувало бы ленту и буфер дедлайна.
`GET /combat/catalog` отдаёт `cards` с `rules_text` и отдельный viewer-safe
`statuses`-словарь (`id`, имя, короткое описание, icon-key, decay). Текущие
стаки и ttl принадлежат конкретному unit payload; описание статуса не живёт во
фронтовом дублирующем словаре (U4/W1a).
Срез каждого живого юнита в `snapshot.units` включает также
`remaining_steps`/`remaining_attacks`: UI уменьшает счётчики действий по кадрам
серверных событий, а вне реплея показывает полные базовые характеристики.
Там же — `stance_turns_left` (V6): серверное «ходов до самостоятельной смены
стойки» (`engine/units.py`; null = не сменится) — число на иконке стойки; в
unit payload матча оно тоже есть, клиент его не вычисляет.
Срез игрока в `snapshot.players` несёт `mana` и публичные
`deck_count`/`hand_count` (U3: стопка колоды убывает на кадре `card_drawn`);
состав руки и порядок колоды в снапшоты не попадают никогда.
`from/to_position.row` допускает призрачные ряды башен `-1` и `rows`; это
координата анимации, а не допустимая клетка размещения карты.
`sequence` — сквозной номер события в ходе (уникальный, строго растёт).
`micro_step` — номер итерации резолвера (микрохода): спавны сетапа = 0,
микроходы = 1, 2, 3…; повторяется у всех событий одной итерации. Клиент по нему
отличает «та же итерация» (короткая пауза) от «следующая» (длинная пауза, §18.3
COMBAT_REWORK) — источник счётчика `MatchState.current_iteration`.
Снапшот делается в момент эмиссии; атакующие события эмитятся до применения
урона (снапшот пре-урона), поэтому `after_hp` — авторитетное значение урона.
Клиент обязан: юниты, пропавшие из снапшота, живут до своего DEATH-события.
**HP в пределах хода НЕ монотонен** (переработка v4 снимает потолок HP и вводит
лечение — COMBAT_REWORK §19 C3): анимации должны уметь и рост HP (heal-события),
а не только убывание. (До внедрения v4 HP в ходе фактически только убывает.)

### 2.2 API-слой

- `routes/combat.py`: `GET /combat/catalog`, `POST /combat/start`,
  `GET /combat/{id}`, `GET /combat/active`, `POST /combat/plan` (V3:
  сохранить последний план хода), `POST /combat/ready` (готовность/отмена,
  несёт план атомарно), `POST /combat/resolve` (ручной/тестовый путь;
  валидация: turn актуален, карты в руке; просроченный ход → 409 и серверный
  дорезолв), demo.
- `routes/auth.py`: email-код (dev), **реальный Google OAuth** — `GET
  /google/login` (редирект на Google, state-кука против CSRF) и `GET
  /google/callback` (обмен кода через `services/google_oauth.py`, identity по
  `sub`, refresh-cookie, редирект на фронт; любая ошибка → `?auth_error=google`);
  `GET /providers` — какие способы входа включены (фронт строит кнопки по нему);
  Google dev-login (только `environment=local`), refresh-cookie, logout.
  Секреты/URL — env через `core/config.py` (`google_oauth_*`, `frontend_url`,
  `cookie_secure`).
- `routes/me.py`: профиль, коллекция (+ ascend — подлежит отключению, см. §7).
- `services/combat_turn_timers.py`: дорезолв матчей с истёкшим дедлайном.
  Вызывается и лениво из роутов, и фоновым воркером
  `services/combat_timer_worker.py` (asyncio-задача в lifespan, тик 1 с,
  broadcast в WS-канал матча) — AFK-игрок не блокирует матч. Результат любого
  пути — единый resolution-envelope: финальный `match`, явный `resolved_turn`,
  `last_sequence` и полная `events`. Последний envelope хранится внутри
  `BattleStateV4` (`last_resolved_turn`/`last_events`), поэтому lazy GET и
  reconnect не превращают завершённый ход в eventless-снап.
- `domain/combat/engine/payload.py`: сериализация v4-матча наружу, **payload
  viewer-специфичен** (`viewer_id` в ответе): колода игрока не сериализуется
  никогда (только `deck_count`), рука уходит только её владельцу (остальным —
  пустой список + `hand_count`), `user_id` наружу не отдаётся.
- `services/rewards.py`: идемпотентная выдача награды (unique user+match).
- `services/dev_logging.py`: JSONL-логи в `.dev/` для отладки боёв.

### 2.3 Хранилище

SQLAlchemy + Alembic. Таблицы: users, auth_identities, email_login_codes,
refresh_sessions, audit_log, player_profiles, card_definitions (пока legacy-
проекция из `domain/combat/cards.py`; рассинхрон с live v4 — §8.18),
player_cards (user, card, ascension→убрать, copies),
combat_reward_claims (уникальность user+match), combat_matches (**состояние
матча — JSON-блоб `state_json`**, статус/владелец — колонками для выборок).

Решение: состояние боя как JSON — осознанное (быстрая эволюция правил без
миграций); индексируемые поля выносятся в колонки.

### 2.4 Realtime

`realtime/match_channels.py`: in-process менеджер каналов по match_id.
WS `/ws/matches/{id}`: снапшот при подключении, `match.updated` после каждого
резолва (руками роутов), ping/pong. Клиент имеет polling-fallback (8 с), когда
WS не подключён. Одного инстанса достаточно для цели 100–200 CCU; Redis pub/sub —
только при переходе на несколько инстансов (Р2+).

### 2.5 Деплой (prod)

Один VPS, один домен, `deploy/docker-compose.prod.yml` (инструкция —
[DEPLOY.md](DEPLOY.md)): Caddy (образ web, multi-stage `VladStoneWeb/Dockerfile`
c `target: prod`) раздаёт статику фронта и проксирует `/api` + `/ws` в
uvicorn; PostgreSQL — только во внутренней сети. Same-origin убирает
CORS/куки-боль (фронт собирается с `VITE_API_BASE_URL=/api`). HTTPS — авто
(Caddy). Миграции — на старте контейнера API (`alembic upgrade head`);
`init_db`/create_all вне local/test отключён. **Один uvicorn-воркер** — WS и
таймер in-process (§2.4). Прод-режим включается `ENVIRONMENT=production`:
гасит dev-login, email-коды и create_all; `COOKIE_SECURE=true`.

## 3. Frontend

- `src/features/battle/` — бой: `BattleV4.tsx` + `useTurnPlayback.ts`
  (оркестрация и покадровый replay; **авто-отправка расстановки на нуле
  видимого таймера** — показ капается серверным `planning_seconds` из payload
  (эндшпиль сжимает время хода, DESIGN §3.5), а серверный дедлайн больше на
  буфер анимации, этот буфер и есть запас против гонки (прежние «2 с до
  дедлайна» — поведение удалённого MVP); **watchdog анимаций** — зависший ход
  принудительно доигрывается до итога, срок — `WATCHDOG_MS` в
  `animationConfig.ts`; в телеметрию НЕ репортится — `sendClientEvent`
  объявлен, но фронт его сейчас нигде не вызывает), `turnPlayback.ts` (применение серверных
  event snapshots), `battleAnimations.ts` (выпады, попапы, области эффектов),
  `animationConfig.ts` (тайминги; скорость фиксирована — онлайн),
  `matchRealtime.ts` (WS + статус). `unit_waited` временно подсвечивает только
  указанный сервером токен и выводит его причину; это часть реплея, не
  клиентский вывод поведения юнита. `BattleV4` также передаёт viewer-safe
  `statuses` из `/combat/catalog` в W1-инспектор и общий `CardDetail`:
  покрытия рассчитываются из каталожных относительных смещений и `unit.side`,
  а текущие статы/стаки/ttl берутся только из unit payload. Detail не получает
  скрытую руку или порядок колоды; для карты руки он возвращает только явное
  клиентское намерение выбрать её для постановки/цели. Башни и иные юниты без
  `card_id` используют тот же presenter со специальным локальным описанием,
  не запрашивая несуществующую карту из каталога.
- Юниты рендерятся в overlay-слое (`unit-layer`) с transform-позиционированием
  по --col/--row — скольжение между клетками и удары идут CSS-анимациями,
  синхронизированными с серверными событиями (урон применяется в момент удара).
- `src/shared/`: `Card.tsx` (лицо карты 4:5, квадратный арт), `cardArt.tsx`
  (авто-подхват артов `assets/cards/<card_id>.png` и фонов редкости
  `assets/rarities/<rarity>.png` через import.meta.glob), `icons.tsx`
  (иконки статов, `currentColor`), `apiClient.ts` (base URL, cookie).
- Каталог карт приходит с API (`/combat/catalog`) — фронт не хранит статы.
  `CardDetail` коллекции берёт из него правила, статы, обе схемы покрытия и
  spawn zone; legacy-объект коллекции передаёт только состояние владения
  (копии/возвышение) до закрытия split-brain из §8.18.
- Рука — серверная (`match.players[viewer_id].hand`), планы локально резервируют
  карты руки.
- i18n: зачаток `src/i18n.ts`; целевое состояние — все строки в каталоге (§7).

## 4. Ключевые инварианты

1. Клиент шлёт **только намерения** (placements, старт, resolve); состояние
   считает сервер.
2. Порядок колоды — серверный секрет (`deck_count` наружу).
3. Награды идемпотентны (unique constraint).
4. Анимации = функция от серверных событий; поле должно быть реконструируемо
   из снапшотов событий.
5. Дедлайн хода включает буфер анимации; сервер дорезолвит просроченное сам —
   AFK-игрок не блокирует матч.
6. Правила боя (domain) не знают про HTTP/БД/WS — тестируются в чистую.
7. **`card_id` вечен** (решение R15): карты не удаляются из БД и не
   переименовываются; вывод из оборота — только отключением (§5.6).

## 5. Целевая архитектура Релиза 1

### 5.1 Движок боя v4 — способности, эффекты, стойки (O4; дизайн — COMBAT_REWORK)

> Игровые правила v4 (стойки, 5 башен, порядок фаз, комбо) — в
> [COMBAT_REWORK.md](COMBAT_REWORK.md). Здесь — как это реализовать
> **расширяемо, детерминированно и отказоустойчиво**. Строится в
> `app/domain/combat/engine/` **рядом с MVP-правилами** (живой бой обслуживает
> старый код до подмены в конце P2 + bump RULESET_VERSION). Реализовано (июль
> 2026): сущности (P2.8), словарь Effect/TargetSelector + исполнение (P2.9),
> семифазный резолвер с волновой моделью (P2.10, `resolver.py`),
> validate_state после каждой фазы + канонический дамп состояния (P2.11);
> клиентские события, бот, поле/башни — следующие шаги COMBAT_REWORK §20 P2.

**Три цели движка:** (1) новая карта = данные, не код; (2) полный детерминизм
(бой воспроизводим, просчитывается руками — аксиома 3); (3) отказоустойчивость:
противоречия ловятся движком, а не всплывают багами в бою.

#### Сущности (данные)

- **Карта ≠ юнит** (COMBAT_REWORK §10): `CardDefinition` (коллекционное:
  id, name, cost, rarity, `card_type: unit|spell`, art, `collectible: bool`)
  ссылается на `UnitBlueprint` (для юнит-карт) или `SpellScript` (для
  заклинаний). **Токены** — `collectible=false`: полные статы и мана-цена,
  призываются эффектами, в коллекции нет, с руки не играются.
- **`UnitBlueprint`**: базовые статы (hp, damage, `attacks_per_turn`,
  move_steps), `stance_program` (врождённое расписание стоек), `coverage:
  {stance: CellPattern}` (зона атаки на стойку), `spawn_zone: CellPattern`,
  `tags: set[str]`, `abilities: list[Ability]`.
- **`UnitState`** (рантайм): ссылка на blueprint, current_hp, position, side,
  `statuses: list[Status]`, `turns_on_field`, производная `stance`, теги
  (базовые + выданные). Башни — тоже `UnitState` (blueprint с вечной Защитой,
  `attacks_per_turn`, тег `immovable`).
- **`Status{id, stacks, ttl}`**: единый механизм для яда, щита, **и наложенной
  стойки** (forced-stance — статус с ttl, маскирующий врождённую стойку).
  Один механизм вместо двух — меньше кода, меньше багов.
- **`Ability{trigger, effect, target}`**. Триггеры-хуки конвейера:
  `on_spawn, on_turn_start, on_attack, on_damaged, on_death, on_turn_end,
  on_stance_change`. Заклинание — `SpellScript{id, actions: [{effect,
  target}...]}` (отыгрывается в спелл-фазе в submission-порядке, C1);
  опциональные `condition` у способностей добавим, когда появится первая
  карта с условием — пустую модель условий не строим.
- **`Effect`** — примитив из **фиксированного словаря** (deal_damage, heal,
  apply_status, change_stance, spawn_token, push, kill_if, draw_card,
  modify_mana, grant_tag…). Карта комбинирует известные примитивы —
  произвольного кода на карту нет (ключ к отказоустойчивости).
- **Цикл колоды v4**: `EffectContext.deck_card_ids` получает decklist конкретного
  live-матча. Пустая колода пересобирается из карт этого списка вне текущей
  руки; `None` допустим только в изолированных тестовых/скриптовых контекстах
  без deck-cycle. Поэтому v4 никогда не обращается к legacy `DECK_CARD_IDS`.
- **`TargetSelector{area, side_filter, tag_filter?, …}`**: area — CellPattern/
  вся доска/клетка; `side_filter` по умолчанию **any** (friendly fire по
  дефолту, E2); карты сужают (enemy/ally/по тегу). Заклинания таргетят по
  клетке/зоне (§13.2), фильтр отбирает юнитов в зоне.

#### Стойка — производное состояние (устраняет класс багов)

`stance` НЕ хранится как изменяемое поле-истина. Каждый ход одна чистая функция
выводит её из `(stance_program, turns_on_field, активные forced-stance
статусы)`. Наложение стойки = статус с ttl; по истечении юнит возвращается к
тому, что говорит врождённая программа сейчас. Так «застрявшая стойка» и
противоречия «два источника правды» невозможны by design (COMBAT_REWORK §18.6,
F1–F3 — уточнить возврат/приоритет пределов).

#### Резолвер: фазы + волны + шина хуков

Ход резолвится строго по **7 фазам** (COMBAT_REWORK §18.5): заклинания →
смерти-волна → спавн(+on_spawn, мини-волна) → итерации юнитов (башни тут) →
эффекты конца хода → смерти-волна → добор. Смерти в фазе — **волновой моделью**
(H3): снапшот → накопить урон → одновременная волна смертей → on_death в
порядке чтения поля → повтор, пока есть смерти; каждый юнит гибнет/триггерит
один раз. Хук-шина: фазы объявляют точки, способности/статусы подписываются;
**единый тайбрейк везде — порядок чтения поля (ряд, колонка)**.
**Фаза заклинаний — последовательна по игрокам с чередованием порядка по ходам**
(решение C1, COMBAT_REWORK §19): монетка (сид в MatchState) на 1-м ходу задаёт
первого, дальше меняются; заклинания первого (submission-порядок) → волна
смертей → заклинания второго → волна смертей. Убирает одновременные конфликты
каст-vs-каст.

**Цикл хода и мана параметризуемы** (R13): «доп. ход», «кража маны» —
легальные Effect'ы над состоянием очереди фаз/бюджета, не хаки.

#### Детерминизм и отказоустойчивость (анти-баг)

- **Ноль скрытого рандома**: только явный `draw_random` через сид в MatchState.
- **Один тайбрейк** (чтение поля) для таргетинга, волн смертей, порядка хуков —
  одно правило на весь бой.
- **Снапшот на фазу** — одновременность встроена (никаких «кто применился
  раньше»).
- **`validate_state()` после каждой фазы** (в dev/тестах — assert): HP в
  [0..max], одна клетка = один юнит, позиции в границах, ttl ≥ 0. Противоречие
  падает сразу у источника, а не багует через 10 ходов.
- **Чистый домен** (инвариант §4.6): без I/O, весь бой юнит-тестируем; каждый
  примитив Effect — свои тесты; каждая карта — дата-фикстура, гоняемая
  симуляцией. Балансовые сценарии (спам, стена vs сплеш, катапульта vs раш) —
  регресс-набор (DESIGN §4.4).
- **Реплей-запись** (единый источник воспроизведения матча): `rng_seed` в
  `MatchState` при создании — весь рандом производный (`seed + turn + counter`);
  плюс append-only журнал **фактически применённых** намерений по ходам
  (`turn_intents`). Одного seed мало: дедлайн-автосабмит делает набор намерений
  зависящим от времени прихода, поэтому что именно применилось — надо хранить.
  Реплей = прогон резолвера над `(rng_seed, начальная конфигурация, журнал
  намерений)`; детерминированная сериализация + `validate_state` дают бит-в-бит.
  Полные snapshot'ы остаются только дебагом, не источником истины (поле и так
  реконструируется из событий, инвариант §4.4). Закрывает риск §8.16.

#### Расширения движка под батч №1 (✅ реализовано, июль 2026)

> Расширения под утверждённый ремап 12 карт (COMBAT_REWORK §14.1). Каждое —
> переиспользуемый механизм, не костыль под одну карту. Все реализованы и
> покрыты тестами (test_engine_extensions.py); бюджеты действий при этом
> переехали из фазы итераций в НАЧАЛО хода (бафы бюджета из спелл-фазы
> обязаны доживать до итераций) и выдаются при спавне (D4).

1. **Пресеты паттернов** (нужны почти всем картам): фабрики на `CellPattern` —
   `cross(radius=1)` (по radius клеток в 4 стороны), `ring()` (8 клеток
   вокруг), `square(include_center=False)` (3×3). Дальник = `ring() +
   cross(2)`, взрыв Черепа = `square(include_center=True)`. Чистые данные,
   любая будущая карта их переиспользует.

2. **Новый тик яда + спецификации статусов**: реестр статусов из плоского
   набора id становится таблицей `StatusSpec{id, decay: ttl|stacks|permanent,
   tick_damage: int = 0, tick_heal: int = 0}`. Яд = `decay=stacks,
   tick_damage=1` (−1 HP и −1 стак за ход, канон §14.1); клеймо Задания и
   наложенная стойка = `decay=ttl`; будущие регенерация (`tick_heal`) и щит —
   строки таблицы, не код. Единый тик фазы 5 читает спеку.

3. **Эффективные статы — одна точка чтения**: функция
   `effective_stats(unit, blueprint) -> UnitStats` = базовые статы чертежа
   → поверх стойко-зависимый оверрайд → поверх перманентные бафы юнита.
   Резолвер и башни читают статы ТОЛЬКО через неё (сейчас — напрямую из
   чертежа в нескольких местах; прямое чтение объявляется багом). Это
   несущая стена для пп. 4–5.

4. **Стойко-зависимые статы** (Эпик Серёга: урон 5 в Защите / 3 в Атаке):
   опциональный `stats_defense: StatsOverride` на чертеже — частичные поля
   (damage/attacks_per_turn/move_steps), по аналогии с per-stance покрытиями
   (§10.4 — «у юнита в защите и атаке разные зоны» распространяется на
   статы). Любая будущая карта «в стойке X быстрее/злее» — данные.

5. **Бафы статов** (Задание: +3 HP и +1 атака навсегда; Самурай: +1 шаг в
   этом ходу):
   - перманентные: `UnitState.permanent_bonuses: StatBonus{hp, damage,
     attacks, steps}` (дефолт нули) + новый примитив словаря
     `buff_stats{..., permanent}`; HP-бафф поднимает и current_hp
     (потолка нет, Q4). Учитывается в effective_stats;
   - временные «в этом ходу»: новый примитив `modify_budget{steps|attacks,
     +n}` — правит remaining_* текущего хода, ничего не хранит между ходами.
     Переиспользуемо: «ускорение», «доп. атака в этом ходу».

6. **Триггер-наблюдатель смерти** (Самурай: «+1 шаг после смерти врага в моём
   радиусе атаки») + **скоуп self**: новый хук `on_enemy_death_in_coverage` —
   волна смертей после каждого поколения перебирает живых наблюдателей с этим
   хуком (в порядке чтения поля): умерший враждебен и стоял в текущем
   покрытии наблюдателя → отыграть эффект способности. Срабатывает за КАЖДУЮ
   подходящую смерть (стакается за ход). Плюс `TargetSelector.scope="self"` —
   цель = сам носитель (нужен и другим будущим способностям).

7. **Квест-статусы** (Задание): `StatusSpec` получает опциональный блок
   `end_of_turn_quest{condition, on_success: [Effect], on_fail: [Effect]}`,
   исполняемый в фазе 5 ДО тика ttl. Условия — фиксированный словарь (как
   эффекты), первое: `attacked_unit_that_died_this_turn` — проверяется по
   фактам хода (резолвер уже копит EngineEvent'ы: атака клеймлённого ∧ смерть
   цели в этом ходу). Задание = клеймо `decay=ttl(1)` + квест-блок:
   success → `buff_stats{hp+3, attacks+1, permanent}`, fail → казнь (doomed).
   Любые будущие «проклятия/контракты» — данные той же формы.

#### Карты в руке/колоде: add_card и CardInstance (спроектировано июль 2026, НЕ реализовано)

> Решения владельца — COMBAT_REWORK §25 (дубли в рантайме ок; кэп руки 6; при
> полной руке карта не добавляется никуда). Две независимые части: дешёвая
> (add_card) и модельная (CardInstance). Реализация — отдельными этапами по
> отмашке владельца.

**Часть A — эффект `add_card` (мелкая, не ждёт часть B):**

- Новый примитив словаря: `AddCard{card_id, destination: hand|deck,
  recipient: caster|enemy}`. Добавлять можно только карты статичного контента
  (content.py), включая токены `collectible=false` — генерации карт на лету
  нет. Валидация card_id — на загрузке контента (I7), не в бою.
- Детерминизм (A2/A3): вставка в колоду — **в низ** (позиция фиксирована,
  rng не нужен); вариант «вмешать случайно» — только позже через сид
  MatchState. Дубли легальны (решение владельца).
- Правила отказа: `destination=hand` при руке в кэпе (`HAND_CAP` 6) →
  наблюдаемый `fizzled`-факт, карта НЕ добавляется никуда (без фолбэка в
  колоду — решение владельца). `destination=deck` — кэпа нет, всегда успех.
- Событие: новый факт `card_added{player_id, card_id, destination}` →
  CombatEvent. **Анти-чит:** наружу `card_id` уходит только владельцу
  получившей стороны; остальным — только факт и обновлённые
  `hand_count`/`deck_count` (в PvE один viewer — уже ок; для PvP это тот же
  per-viewer контракт, что и R2 из §21). Порядок колоды секретом остаётся.
- Экономика/коллекция не затрагиваются: бой не мутирует аккаунт, добавленные
  карты живут только в состоянии матча.

**Часть B — `CardInstance`: баффы/дебаффы карт в руке и колоде (средне-крупная):**

- Модель: `PlayerState.deck/hand: list[CardInstance]`;
  `CardInstance{iid, card_id, modifiers: CardModifier}`.
  `iid` — детерминированный счётчик матча (аналог `token_seq`), НЕ uuid —
  сериализация и реплей остаются бит-в-бит (I3). `CardModifier` — частичные
  дельты: `cost_delta`, `hp`, `damage`, `attacks_per_turn`, `move_steps`
  (форма совместима со `StatBonus`/`StatsOverride`).
- Новый примитив `buff_card{zone: hand|deck|both, recipient, filter
  (card_type/теги), modifiers}`; выбор конкретных карт — детерминированный
  (все подходящие; «случайная карта» — позже через сид, A2 это разрешает).
- **Точка применения баффа юниту — спавн**: `spawn_unit` переносит
  `modifiers` инстанса в уже существующий `UnitState.permanent_bonuses` →
  `effective_stats` учитывает их без нового кода чтения статов.
  `cost_delta` учитывается в валидации розыгрыша (мана).
- Намерения: `SpawnIntent`/`SpellIntent` получают `instance_id` (валидация
  «карта в руке» — по iid, а не по card_id; закрывает и двусмысленность двух
  одинаковых копий в руке).
- Payload: владельцу — рука списком инстансов (card_id + modifiers, UI
  показывает буст поверх каталожных статов); противнику — как сейчас только
  `hand_count`/`deck_count`. Колода не сериализуется никогда.
- **Deck builder не блокируется**: БД (`player_decks.card_ids`) и коллекция
  остаются на уровне `card_id`; инстансы создаются фабрикой матча из
  decklist. Точка сопряжения одна — старт матча.
- Цена: смена формы состояния → bump `RULESET_VERSION`; рефактор
  `deck.py`-цикла (раздача/добор/перетасовка по инстансам), фабрики руки,
  `BattleV4`-руки (ключи по iid) и тестов. Событ/анимация «карта в руке
  усилилась» — viewer-only событие для владельца.

**Порядок, если/когда владелец даст отмашку:** сначала часть A (примитив +
тесты + событие), затем часть B одним этапом с bump'ом версии правил; первые
карты-потребители — только после плейтеста базового батча (Фаза 2).

#### Готовность к босс-режиму (оценка, июль 2026)

Босс «1 против 4, широкое поле, уникальные карты, куча маны» — почти целиком
данные. Уже готово: N участников/команды/стороны (бой двух сторон при любом
числе игроков), per-player колода/рука/мана (R12/O12), неколлекционные карты
(collectible=false — карты босса не попадают игрокам), параметрическое поле,
спелл-очередь по N игрокам. Требует мелких правок движка: (1) мана-кривая и
кэпы (мана/рука) — сейчас одни на матч, нужны per-участник (конфиг с
дефолтом); (2) башни ставятся «на игрока» — для коопа нужны «на команду»
(+ вопрос владельцу: у босса башни или он сам — большая цель). Отдельно и
позже — кооп как продукт: лобби/инвайты/мульти-клиент (Фаза 4).

#### Размер поля — параметр режима (требование владельца, июль 2026)

Разные режимы/боссы будут играться на полях разных размеров. Контракт:
движок принимает `rows`/`cols` параметрами (уже так); сервер шлёт размеры в
payload матча (уже так, `MatchState.rows/cols`); **клиент строит сетку и всю
геометрию ТОЛЬКО от присланных размеров** — никаких «cell % 3», жёстких
спавн-клеток и фиксированных CSS-сеток (текущий хардкод фронта выпиливается
на интеграции v4). Зоны спавна карт клиент берёт из данных каталога (у каждой
карты своя зона) — не выводит из размера поля.

#### Расширяемость (лёгкость добавления карт)

- Ванильный юнит = одна запись данных (статы + coverage + spawn_zone).
- Карта с механикой = композиция примитивов в данных; новый примитив нужен
  редко — добавляется раз, тестируется раз, переиспользуется всеми.
- События расширяются `ability_triggered, status_applied/expired, spell_cast,
  stance_changed` — клиент анимирует по ним (контракт §2.1).

### 5.2 PvP: модель участников и синхронизация

**Модель участников (R12) реализована** (июль 2026, `RULESET_VERSION` 2):

- **Матч = N участников в командах**: у `PlayerState` есть `team` (сторона поля
  выводится из команды — `board.side_for_team`), `is_bot`, `user_id`,
  per-player `deck`/`hand`; `bot_spawn_count` — в state бота (поле
  `PlayerState`). Хардкода `"player"`/`"bot"` больше нет: PvE-места создаются
  с нейтральными id `p1`/`p2`, участники ищутся по роли
  (`helpers.human_players/bot_players`) или `user_id`. Конец матча — по
  командам (`lifecycle`): матч завершается, когда команда выбита; победитель —
  единственная живая команда (`result.winner_team`, для 1v1 плюс `winner_id`).
- **Мана в коопе** (решение O12, июль 2026): бюджет маны — **у каждого игрока
  свой** (пул на `PlayerState`, не общий на команду). Мана-счётчик и
  мана-расписание оперируют per-player бюджетом; так 1v1, кооп и 2v2 — одна
  модель без развилки.
- Сериализация: каждому клиенту — **его** рука и только `deck_count`/`hand_count`
  всех участников; рука соперника наружу не уходит (анти-чит). Ответ несёт
  `viewer_id` — клиент находит «себя» по нему, врага — по чужой `team`.
  Payload юнита отдельно несёт эффективные базовые HP/урон/шаги/атаки и
  оставшиеся бюджеты действий; UI планирования показывает базовые значения.
  PvE-допущение: получатель по умолчанию — единственный человек матча
  (`combat_response`); per-socket viewer'ы — вместе с invite flow ниже.

**Reliability резолва после A6 — ✅ закрыто (июль 2026).** HTTP
`POST /combat/resolve`, WS `match.updated`, timer-worker и lazy-resolve используют
единый `ResolvedTurnEnvelope`: `{match, resolved_turn, events, last_sequence}`.
Таймерные сервисы возвращают состояние вместе с фактами, broadcast принимает
их явно, а последняя полная лента хранится в `BattleStateV4` до следующего
резолва. Клиент проигрывает первый полный источник и дедуплицирует остальные по
`(match_id, resolved_turn, last_sequence)`; полноценное WS-эхо не теряется даже
во время собственного HTTP resolve/409. Связанный сбой сериализации атак башен
на призрачных рядах также закрыт отдельным `EventPosition`. Детали и регрессии —
COMBAT_REWORK §23.1.

Осталось для PvP (целевое состояние):
- Планирование: все участники шлют placements до дедлайна; резолв — когда все
  подтвердили «готов» или по таймеру. Ранний резолв при полном наборе confirm.
- Invite flow: `POST /matches/invite` → токен/ссылка → `POST /matches/join`.
  Матч в статусе `waiting_for_opponent` до присоединения.
- Reconnect: WS-снапшот при подключении + `/combat/active`. **Контракт
  дозагрузки посреди хода** (закрывает риск §8.15): сервер отдаёт снапшот
  *начала последнего хода* + список combat-событий этого хода +
  `resume_from_sequence`; клиент проигрывает ход с начала (анимация — чистая
  функция от событий, инвариант §4.4), дедуплицируя по `(turn, sequence)` —
  расширение уже существующего отбрасывания «WS-эха своего резолва». Уже
  показанные ходы клиент проматывает к финалу по `resume_from_sequence`.
  Источник истины анимации — события, не снапшот.
- Concede: `POST /combat/{id}/concede` → немедленный `match_finished`.
- **Взаимная бездеятельность** (решение O11, июль 2026): отдельного AFK-детектора
  и раннего завершения **не вводим** — исход обычный (поражение = AFK, DESIGN

  `enabled_from/until` для ивентовых — не сейчас).
- Отключённая карта не должна встречаться игроку **ни на одном слое**; проверки

  5. **Планирование**: placement неактивной карты отклоняется доменом
     (последний рубеж).

14. **Таймер-воркер — единая точка и совпадение дедлайнов** (blindspot, июль
    2026): один asyncio-тик 1 с (`combat_timer_worker.py`); при 100–200 CCU
    совпавшие дедлайны резолвятся в один тик (пик CPU + залп broadcast), а падение
    воркера замораживает матчи для WS-клиентов с выключенным поллингом.
    **Решение:** (1) детерминированный джиттер дедлайна из `hash(match_id)`
    (0…~2 с) разводит дедлайны, но НЕ влияет на результат резолва (джиттер из id,
    не из wall-clock — детерминизм цел); (2) кап на число матчей за тик (старейшие
    дедлайны первыми, остальное — следующим тиком; буфер в дедлайне это скрывает);
    (3) heartbeat воркера в метрику. Ленивый дорезолв в роутах остаётся гарантом
    корректности: падение воркера = деградация задержки, не потеря матча.
    Мульти-инстанс (Redis/шедулер) — только Р2 (§8.4).
    **Живучесть тика — закрыта (июль 2026, V3-фикс):** воркер молча умирал от
    ПЕРВОЙ записи с нечитаемым state (MVP-форма, ошибочно сохранённая с
    текущим `ruleset_version` в переходном окне подмены движка проходила
    version-гейт), что маскировалось клиентским автосабмитом. Теперь
    per-record исключения не роняют тик: нечитаемый state гасится как expired
    (принцип гейта §8.7, `expire_combat_match_unreadable`), прочие ошибки —
    лог + следующий матч; вокруг тика — последний рубеж try/except.
    Heartbeat-метрика воркера остаётся открытой (п.3).
15. **Реконнект посреди хода — контракт дозагрузки** (blindspot, июль 2026):

    *поток* событий; догоняющий клиент рискует показать финал без анимации либо

    хода + события хода + `resume_from_sequence`, дедуп по `(turn, sequence)`).

    разрыве WS. Это не заменяет будущий resume-контракт для PvP.

    реально начнут грузить воркер (не сейчас).
18. **Split-brain каталога v4 и коллекции — закрыто** (август 2026): один
    прикладной каталог `engine/catalog.py` читает live-определения из
    `engine/content.py` и кормит DB projection, выдачу, `/me/collection` и
    будущую валидацию колод. `/me/collection` возвращает ровно viewer-safe
    метаданные `/combat/catalog` плюс количество копий; это охраняет
    контрактный тест. При следующем входе существующий аккаунт получает
    недостающие карты live-набора. Legacy-каталог приложения удалён; старый
    изолированный MVP combat domain остаётся только для его регрессионных
    тестов, не участвует в live-маршрутах. Возвышение отключено в UI и API
    согласно R9; исторические DB-колонки пока сохраняются до решения O2.
19. **WS broadcast без backpressure — закрыто для текущего процесса** (август
    2026): у каждого подключения есть ограниченная outbound queue и отдельный
    sender task с send-timeout. Переполненный или сломанный сокет отключается,
    поэтому HTTP/DB commit и timer-worker не ждут медленного клиента. Есть
    регрессионный тест не читающего сокета. Перед multi-instance PvP понадобится
    общий pub/sub transport (ARCH §8.4).
20. **Лимиты combat/WS input — частично закрыто** (август 2026): введены
    Pydantic bounds на id/координаты и максимум 6 placement/spell intents; WS
    закрывает не-JSON и сообщения свыше 4 KiB; ASGI отбрасывает HTTP body свыше
    16 KiB до JSON/Pydantic разбора. До public release остаётся общий limiter
    между инстансами и интеграционные 429-тесты.
21. **Проверка Google ID token — закрыто** (август 2026): вместо ручного
    base64 decode используется `google-auth`. Он проверяет подпись по Google
    public certs, audience и срок token; код дополнительно допускает только
    официальные `iss`. Тесты подменяют verifier, включая отказ для
    неподписанного token. `azp` потребуется, если появится несколько client
    ids; текущая конфигурация принимает ровно один.
22. **Python-зависимости production не зафиксированы — release/reproducibility**
    (аудит 15 июля 2026): `pyproject.toml` задаёт только нижние границы, CI и
    Docker каждый раз выполняют новый `pip install`, поэтому одинаковый commit
    может собрать другой набор транзитивных версий или внезапно перестать
    собираться. Frontend уже имеет `package-lock.json`. **Фикс:** генерируемый
    lock/constraints с hashes для Python; CI и Docker ставят ровно его;
    Dependabot/Renovate обновляет отдельными проверяемыми PR.
